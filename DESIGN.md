# Design Note — Self-Improving Patient Scheduling Agent

## Key design choices

I kept the system deliberately small: one scheduling agent, explicit conversation state, five narrow clinic tools, and a deterministic in-memory clinic store. The language model handles natural conversation and intent resolution, while clinic truth stays outside the model. Availability, booking status, cancellation, and rescheduling are valid only when supported by tool output. Deterministic guardrails sit between model requests and state-changing tools, so important safety behavior does not rely only on prompt compliance.

## Evaluation philosophy

The harness evaluates more than the transcript. For each scenario it inspects required and forbidden tool calls, failed mutations, final appointment state, and selected response requirements. Hidden clinic state receives the highest importance because a fluent answer can still be operationally wrong—for example, the assistant can say “your 2:30 appointment is booked” while the database contains no booking or the wrong slot. Each scenario gets both a pass/fail verdict and a weighted score, and the suite reports category scores, critical failures, and regressions.

## How the improvement loop works

A failed evaluator check becomes structured evidence containing the scenario, failure code, category, criticality, expected state, and observed state. Only allow-listed failure classes can produce a reinforcement rule; the agent is not allowed to rewrite its own prompt arbitrarily. The candidate rule is appended to the learned-reinforcement section of the system prompt and the exact same scenarios are run again. The rule is promoted only if there is measurable improvement, the total score does not decrease, and there are zero regressions. Otherwise the reinforcement file is restored automatically.

**Before / after score:** generated by the real model run and saved in `reports/latest_eval.json`. I intentionally do not hard-code a claimed score here before running the configured model.

## What I would change for a real clinic

The mock clinic store would be replaced by authenticated EHR/scheduling APIs with patient identity verification, PHI minimization, role-based authorization, audit logs, idempotency keys, transactional booking semantics, retry/error policies, observability, rate limits, human escalation, and clinic-specific safety/compliance review. I would also version prompts/evaluators and require offline approval before any learned reinforcement reached production traffic.

## AI assistance vs my judgment

AI assistance was useful for accelerating boilerplate, generating candidate edge cases, and critiquing wording. My engineering judgment determined the tool boundaries, state ownership, deterministic guardrails, hidden-state evaluation strategy, weighted scoring, scenario design, allow-listed improvement policy, and rollback gate. I deliberately chose constrained self-improvement over unconstrained prompt rewriting because this is a healthcare-adjacent workflow where reliability matters more than apparent autonomy.
